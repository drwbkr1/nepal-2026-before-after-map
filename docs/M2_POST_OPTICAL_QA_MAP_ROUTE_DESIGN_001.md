The new candidate differs from the closed projection methods **after** a valid native GTC return. The installed GDAL 3.12.2e runtime reports no `CRF` driver, so it cannot directly warp an ArcGIS CRF. Esri's [`CopyRaster` documentation](https://pro.arcgis.com/en/pro-app/latest/tool-reference/data-management/copy-raster.htm) lists TIFF as a supported output from a raster dataset. A proposed bridge is a new, pixel-value-preserving native CRF-to-TIFF copy with explicit checks of CRS, transform, dimensions, bands, pixel type, NoData, and sampled pixel identity. The copy's georeferencing and value preservation are **not established**; failure ends the method before any projection or real-source continuation.

Only after that bridge passes would GDAL `Warp` target the **exact** frozen EPSG:32645 bounds `[272300, 3069230, 368820, 3150210]` at 10 m, or 9,652 columns by 8,098 rows and 78,161,896 cells. [GDAL's Python API](https://gdal.org/en/stable/api/python/utilities.html) exposes `outputBounds`, `width`, `height`, `dstSRS`, and `resampleAlg`. This is a candidate way to avoid accepting the earlier `ProjectRaster` overshoot while preserving the requested final grid. It must use continuous resampling for gamma data and nearest-neighbor resampling for categorical masks, with explicit NoData and coverage accounting. An exact output frame may contain empty cells; it does **not** create missing SAR coverage or restore detail from a coarse native GTC raster.
